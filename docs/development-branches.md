# 开发与发布分支

| 分支 | 用途 | 何时进入 |
| --- | --- | --- |
| `feat/<name>` | 中大型、跨模块或多人协作需求 | 从最新的 `dev` 开出。未完成的实现、阶段性成果与验证留在需求分支。 |
| `dev` | 已完成需求的集成线 | 需求闭环并通过下列检查后才合入；范围明确、能独立验证的小修复可直接在 `dev` 提交。 |
| `main` | 发布线 | 只有用户明确决定发版后，才接收本次选定、已验收的发布候选。验收通过不等于已获准发版。 |

## 三个方向，别弄反

分支之间只有三种流动，方向、时机、前提各不相同。**看错任何一个方向都会把未完成的活推进稳定线**，所以并排列在这里：

| 动作 | 方向 | 时机 | 前提 | 绝不 |
| --- | --- | --- | --- | --- |
| **回灌** | `dev` → `feat/<name>` | 需求进行中，定期做 | 只为提前解冲突，随时可做 | 反向把 `feat/*` 合进 `dev` |
| **合入** | `feat/<name>` → `dev` | 需求**做完并验收通过**后 | 下面四条全部满足 | 未完成就合入 |
| **发版** | `dev` → `main` | **用户明确说要发版**时 | 已选定并验证的发布范围 | 日常集成顺手更新 `main` |

记住这三行的办法：**回灌是往下流（把主干带进需求），合入和发版是往上流（把成果推向稳定线）**。往下流随时可做、无前提；往上流都必须先满足前提。

## 任何合并都在临时分支上做

**不要直接在任何目标分支上执行 `git merge`。** 先开一个临时分支，在它上面合并、解冲突、跑验证，确认无误后再回到目标分支合并这个临时分支。

```bash
# 例：把 feat/uninstall 合进 dev，不在 dev 上直接 merge
git switch -c merge/uninstall-into-dev dev
git merge feat/uninstall              # 冲突在这里解决
pnpm typecheck && pnpm build          # 验证在临时分支上跑
# 通过后才回到目标分支
git switch dev
git merge merge/uninstall-into-dev
git branch -d merge/uninstall-into-dev   # 用完即删
```

命名建议 `merge/<来源>-into-<目标>`，例如 `merge/uninstall-into-dev`、`merge/dev-into-member-worktree`——名字本身就是方向，写反了一眼能看出来。

**为什么必须这样**：

- **目标分支保持随时可用。** 直接在 `dev` 上解冲突，撞上一时解决不了的冲突就只能卡在半个合并态（`MERGE_HEAD` 挂着、工作区一堆 `UU`），这期间谁都别想在上面正常干活。
- **失败可以整个丢弃。** 临时分支上验证不过，`git branch -D` 就干净了，目标分支从没被碰过；直接在目标分支上做，撤回要 `git merge --abort`，一旦中间又提交了东西就很难干净退回去。
- **验证有落脚点。** 冲突解完必须重跑验证，在临时分支上跑出来的结果对应一个确定的 SHA，可以说清楚「验的是哪一版」。

**临时分支用完即删。** 它只是一次合并的工作台，不代表任何成果；留着会让分支列表看不出哪个是真正在推进的线。

## 何时可以合入 `dev`

中大型、跨模块或多人协作的需求，满足任一条件就从 `dev` 开 `feat/<name>`。合入 `dev` 前，以下条件必须全部满足：

1. 实现已形成可用闭环，需求约定的入口、关键流程和失败处理均已完成。
2. 代码审查已通过，阻塞项已修复并复核。
3. 相关测试及回归已通过；独立验收按确认的清单逐项验证并通过。
4. 待合入版本的 CI 已通过。若回灌或修订改变了候选版本，重新确认受影响的验证结果。

未完成的功能不进入 `dev`，也不进入 `main`。CI 绿是必要条件，不代替审查、测试或独立验收；工作流触发配置本身不启用 GitHub 分支保护，也不自动阻止合并。

## 长分支回灌

延续现有回灌要求：需求分支持续超过一周就定期吸收 `dev` 的更新；遇到拆文件、抽类型、改目录结构等大重构，及时回灌，不攒到最后一次解决。在 `feat/<name>` 上执行 `git merge dev`，解决冲突后复验受影响的范围。回灌方向是 `dev` → `feat/<name>`，不把未完成需求反向合入 `dev`。

大范围回灌同样走临时分支（`merge/dev-into-<name>`），避免把需求分支也卡在半个合并态。

## 何时可以进入 `main`

用户明确要求发版后，先确认本次发布范围和对应的验收结果。如果 `dev` 仍含遗留半成品，或含本次不发的内容，不整支合入 `main`；从 `main` 准备发布候选，只纳入本次明确选定、已验收的改动，并验证组合后的候选及其依赖。候选确认后才进入 `main` 并走发布流程。日常集成、回灌和上游同步不以更新 `main` 为目的。

## CI 触发

`.github/workflows/ci.yml` 对推送到 `main`、`dev` 或匹配 `feat/**` 的分支运行 CI，例如 `feat/member-worktree` 和 `feat/worktree/member`。`pull_request` 触发保持原样，不增加目标分支过滤。以上是 CI 触发规则，不是发布授权；打包与发版仍由 `release.yml` 负责。

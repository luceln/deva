## 零、怎么用这份清单

- **A 系列（必须通过）**：缺任意一条即不可交付。**这是用户视角的承诺**，不是「代码里有个函数」。
- **B 系列（建议通过）**：可与主功能同批，也可紧接一个迭代；缺了要记录，不算失败。
- **本次不做**：明确排除，验收时不得判为缺陷。
- **待澄清**：口径未定。**已有结论的在 §四 标出**，仍未定的列给用户，不自行填默认值。
- **可验标注**：每条末尾 `〔验：…〕` 写明**哪条命令 / 哪个观察**能让它失败。确实无法机械判定的标 **〔不可验〕** 并给替代方案，**不硬凑**（汇总见 §五）。
- **界面项标注**：`〔文案即可〕` = 改 i18n 文案就能满足；`〔需要原型〕` = 涉及布局/交互形态，需先有原型再验收。

术语：
- **引用** = 会话里存的 `"providerId:modelId"` 字符串（每会话一个快照）
- **受影响会话** = 本对话里引用已失效的会话（主对话 + 未移除成员，不含子智能体）
- **体检** = 回合开始前的可用性检查

## 一、A 档 · 必须通过

### 1.1 四类失效认得准

> 提交承诺第 1 条：「模型引用失效分四类识别」。

- [ ] **A1** 服务商被删除（`config.json` 里已无该 provider）时，引用它的会话被判为不可用，且原因是「服务商不存在」这一类。
  〔验：删掉某 provider → 调用可用性判定的 IPC → `kind === 'missing-provider'`（或等价语义），不得是 `nokey` 或 `malformed`〕
  - 报告已排除「服务商被删会误报成缺密钥」（判定顺序先查 provider 存在性），此条为**回归保护**。
- [ ] **A2** 服务商被禁用（`enabled: false`，provider 仍在）时，被判为「服务商被停用」这一类。
  〔验：`enabled:false` → `kind === 'disabled'`；与 A1 的 kind 不同〕
- [ ] **A3** 模型被删除（provider 在、模型 id 不在 `models` 里）时，被判为「模型不存在」这一类。
  〔验：删掉模型 → `kind === 'missing-model'`；与 A1、A2 的 kind 均不同〕
- [ ] **A4** **模型被禁用（`model.enabled === false`，模型仍在）必须单独成类，不得归入「模型被删」**。
  〔验：把某模型 `enabled:false`（provider 仍启用）→ `kind === 'disabled-model'`（或等价语义）；**当前代码归成 `missing`，此条会失败**〕
  - 这是已拍板的分类修正。现状 `model-availability.ts:87` 把 `!model || model.enabled === false` 合并成 `missing`，用户无法得知「是我自己关掉的」。
- [ ] **A5** 缺密钥（provider 在、启用、模型在，但密钥库里没有该 provider 的密钥）时，被判为「缺密钥」这一类，且**与前三类都不同**。
  〔验：清掉该 provider 的密钥 → `kind === 'nokey'`〕
- [ ] **A6** 空引用（`model === ''`）**不判失效**（= 跟随全局默认，它没引用任何具体模型）。
  〔验：`model: ''` → 判定 `ok === true`；界面上该会话不标红〕
- [ ] **A7** 引用格式非法（无冒号 / 任一段为空，如 `':x'`、`'p:'`、`'abc'`）时，被判为「配置异常」这一类，且与「模型被删」可区分。
  〔验：三种形态各测一次 → `kind === 'malformed'`，均不等于 `missing-model`〕

### 1.5 替换结果说得出、留得住

> 提交承诺第 2 条的用户侧后果。**这一组是「不报错但没生效」的最危险一类。**

- [ ] **A21** 界面报「已替换 N 个」后**重启应用**，这 N 个会话的模型仍是新值。
  〔验：替换 → 关闭并重启 → 重读这 N 个会话文件的 `model` 字段，全部等于新值；界面不再标红〕
  - **这是 P1-2 的用户级断言**。现状 `save` 返回 void 吞异常、替换无条件算成功，写盘失败时会「本次运行看着对、重启全变回来」且无任何提示，此条会失败。
- [ ] **A22** 若某个会话**写盘失败**（磁盘满 / 文件被占 / 只读），界面**不得**把它算成「已替换」。
  〔验：把目标会话文件设只读 → 替换 → 该会话不出现在 `changed` 里，或被明确列入失败并说明原因；**不得**静默计为成功〕
  - 与 A21 互为反向证据：A21 验「写成功了要真留住」，A22 验「写失败不能假报成功」。
- [ ] **A23** 替换**目标模型本身不可用**时，**整批拒绝，一个都不改**。
  〔验：目标选一个缺密钥的模型 → 返回 error → 所有候选会话 `model` 与替换前逐一致（`sha256sum` 全不变）〕

### 1.9 换了账户要说清是密钥问题

> 由 P1-1 引出，但断言写在用户侧。

- [ ] **A40** 密钥**存在但解不开**（换 OS 账户 / 换机器 / Linux 缺 libsecret）时，模型被判**不可用**，且提示用户「重填密钥」——而不是判可用、也不是报「模型不可用」。
  〔不可验·环境依赖〕桩环境的 `safeStorage.decryptString` 从不抛错，「有密文但解不开」这个状态在自动化里造不出来。
  **替代方案**（择一，验收时注明用了哪种）：
  ① 真实换一次 Windows 账户手工验（最贴近真实场景，报告 §四 第 2 项推荐）；
  ② 用 `--user-data-dir` 起第二个实例 + 手工篡改 `secrets.json` 密文为无效 base64，让真实 DPAPI 解密失败；
  ③ 代码核查「可用性判定与请求走同一套密钥读取口径」（`hasSecret` 与 `readSecret` 不得分歧）。
  **若三者都做不到，此项记「未验证」，不得记「通过」。**

### 1.10 配置坏了别怪到模型头上

> 由 P1-3 引出，断言写在用户侧。

- [ ] **A41** `config.json` 内容损坏（半截写入 / 手改坏）时，**不得把所有会话集体标红、不得拒绝发送**；用户看到的是「配置读取失败」这类可操作提示，而不是「模型都不可用」。
  〔不可验·进程状态〕`ensureLoaded` 一旦 `loaded = true` 就不再重读，同进程内造不出「坏配置」这个第二态。
  **替代方案**：① 手工把 `config.json` 写成 `{invalid` 后**重启应用**验一次（最直接）；② 每个场景独立进程启动；③ 代码核查「坏配置与空配置被区分对待」。
- [ ] **A42** `secrets.json` 内容损坏时同样不得把所有会话判成「缺密钥」并集体标红，提示方向应指向密钥文件本身。
  〔不可验·同上〕替代方案同 A41。

## 三、本次不做（明确排除，验收不得判为缺陷）

| 项 | 理由 |
|---|---|
| 自动替换（发现失效就自动改） | 用户的模型选择是个人决定，自动改会静默改变他的选择。必须由用户点。 |
| 定时任务自动换模型并改写任务配置 | 定时任务走「回落链」而非「改写」，避免无人值守时改变用户配置 |
| 跨对话/全局批量替换 | 替换的作用域是「本对话 + 成员」，跨对话需先有 A/B 档的全局视图；本次不做 |
| 模型测活（真发一次请求探测可用性） | 判定只依据配置与密钥存在性，不发请求。测活会带来费用、延迟、误判三类问题 |
| 跨窗口并发写保护 | 见 B5；本次不做互斥 |
| 失效模型的自动修复向导 | 只提示类别与动作方向，不做「一键修复」 |
| 「模型被禁用」与「服务商被禁用」的合并展示 | 已拍板独立成类（A4），不合并 |
| 历史中已存在的旧失效记录清理（`session.notices` 里的 error） | 本次只保证**不再新增**（A29），不清理历史存量 |

## 一、模型：新建会话选位置（不是「分叉」）

**不做「从会话分叉」这个概念。** 用户直接新建会话，选位置：

```
新建会话
  位置：  ● 主目录（当前 my/dev）
          ○ 新 worktree
            └ 起点：[my/dev        ▾]   ← 只在选「新 worktree」时出现
            └ 名称：[deva/xxx       ]
```

**为什么放弃分叉**：分叉会继承整段对话历史，而那段历史对应的代码状态可能与新 worktree 的实际内容脱节（主目录有 24 个未提交改动，新 worktree 里一行都没有）。agent 会基于「我熟悉这块代码」的错误认知行动，不再重新读文件。对话越长，脱节越严重。

vibex 的「新会话 = 干净上下文」反而没这个问题：agent 从零读代码，读到什么是什么。

## 二、已拍板的五条

| # | 项 | 决定 |
|---|---|---|
| 1 | 位置默认值 | **主目录**（vibex 做法）。大多数时候不需要并行 |
| 2 | 起点（base） | **用户可选**，选择器默认值为当前分支；候选 = 本地分支 + 远端分支（上限 256） |
| 3 | 合并 | **最小合并**：三项检查 + `git merge --no-ff <source>`，失败显示 git 原始报错 |
| 4 | agent 是否知道边界 | **知道**。会话开始时明确告知「你在独立工作区里，改动需手动合回 <目标分支>」 |
| 5 | 主目录 dirty | 提示未提交文件数量 + 「新工作区不会包含这些改动」，确认后继续 |

## 三、从 vibex 验证过的实现细节（架构可直接采用）

1. **UI 传分支名，执行用 SHA**。`base_ref` 在生成持久化意图那一刻就 `rev-parse` 成 40 位 SHA，之后 `git worktree add -b <新分支> <路径> <SHA>` 全程用 SHA。
   - 原因：`git worktree add <分支名>` 在 UI 选择到实际执行之间，分支可能已前进。「从哪个提交切出」必须冻结。
   - 创建后还要校验新 worktree 的 HEAD === 该 SHA。
2. **`base_ref`（起点）与 `target_branch`（合并目标）是两个字段**，别混。
   - `base_ref` = 用户选的起点
   - `target_branch` = 创建时固定的「源目录当前分支」，即将来合回哪去
3. **合并目标创建时固定，之后不跟随**。用户在终端里 `git checkout other` 后尝试合并 → 明确拒绝（vibex 的 `WrongTargetBranch`）。
4. **worktree 永久固定在自己的分支**，不随主 checkout 换分支而变。
5. **同一分支不能被两个 worktree 同时检出**（`fatal: '<branch>' is already used by worktree at ...`），所以「同一 worktree 多会话」与「多 worktree 共用分支」是两件不同的事——前者合法，后者不行。

## 四、已实测的坑（架构设计时必须考虑）

1. **`git worktree add -b <新分支> <已存在路径>` 会先建分支再失败，留下孤儿分支**。所以失败路径要有分支清理。
2. **detached HEAD 时 `git rev-parse --abbrev-ref HEAD` 返回 `HEAD`**，取不到分支名。默认起点的实现不能只依赖分支名。
3. **`git worktree add` 完全不动主检出**：脏文件原样、index 逐字节不变、`git stash list` 保持为空。
4. **新 worktree 里只有 base 提交的内容**，未提交改动与未跟踪文件都不存在。
5. **worktree 目录被外部删除后**，`git worktree list` 仍列出并标记 `prunable`；对该目录跑 git 命令报 `cannot change to ...`。

## 五、本次明确不做

- worktree 生命周期状态机（vibex 那套 14 状态）
- preflight revision 哈希绑定确认
- 冲突解决面板（冲突时显示 git 报错，让用户去终端）
- 文件重叠预检测（vibex 也没做）
- 每 worktree 独立数据目录（不需要）
- 链式分叉 / 从 worktree 再分叉的专门入口

## 六、仍需架构给出答案的

1. **worktree 回收时机**：会话删除时连带删？分支留还是删？每个 worktree 含一份 `node_modules`（约 15-25MB），磁盘会涨。
2. **分叉数量上限**：要不要？多少？
3. **`pnpm install` 自动跑还是手动**：实测 20-30s，界面上必须显示进度，不能像卡住。
4. **Git 互斥范围**：「同一时刻只允许一个会话执行 git 写操作」还是「各操作自己加文件锁」？
5. **worktree 路径放哪**：必须仓库外（`.deva/` 已被 gitignore，放那里会让「不在仓库内」的断言恒真、验不出东西）。
6. **起点分支选择器的候选来源**：本地 + 远端（vibex 做法，上限 256）还是只本地？
